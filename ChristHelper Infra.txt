CHRISTHELPER – TECHNICAL OVERVIEW (v2 – CURRENT STATE / PRODUCTION + LOCAL)

============================================================
1. PROJECT OVERVIEW
============================================================

ChristHelper is a Christian support platform designed to connect people and ministries that need help with supporters who want to contribute.

The platform supports different kinds of help, including:
- Financial support
- Prayer support
- Guidance / mentorship
- Volunteer help
- Replies / encouragement

Main business idea:
- A user can create a project explaining a Christian need
- Other users can browse projects and support them
- Financial projects go through admin review
- Project owners can connect Stripe to receive funds
- Supporters can donate securely via Stripe Checkout
- Stripe Connect is used so funds can be routed to the project owner
- ChristHelper may also receive a platform support amount

Core functional areas:
- Public project browsing
- Project details page
- Prayer and reply interactions
- User registration and login
- User profile and preferences
- Stripe Connect onboarding and Stripe summary
- Project submission
- Admin review / approval / denial / cancellation
- Donation checkout and webhook processing

9. PAYMENT FLOW (CURRENT DESIGN)
============================================================

Financial support flow:
1. Supporter opens a project
2. Frontend submits donation request to backend
3. Backend validates project status and project owner Stripe status
4. Backend creates local pending donation record
5. Backend creates Stripe Checkout Session
6. Frontend redirects supporter to Stripe
7. Supporter completes payment
8. Stripe sends webhook to production /webhook endpoint
9. Backend verifies signature
10. Backend marks donation as paid
11. Backend updates project.amount_raised
12. Frontend can confirm / refresh and display updated information

Platform support flow:
1. Supporter chooses to support ChristHelper directly
2. Backend creates platform donation checkout session
3. User pays via Stripe
4. Webhook marks donation as paid

Important implementation notes:
- checkout.session.completed is critical
- metadata is used to connect Stripe session back to the local donation
- Without a working webhook, payment may succeed in Stripe but the app state will not update correctly

13. CURRENT LIMITATIONS / RISKS
============================================================

Technical limitations:
- SQLite is fine for now but needs backups
- No formal automated backup process documented yet
- No full email notification system in production yet
- Limited retry / resilience workflow for payment-related operational failures
- Frontend is static and manual-state oriented, not reactive SPA framework-based
- Caching behavior through Front Door may require attention when frontend changes are deployed
- Root domain (christhelper.com) is not yet finalized as a live app entry point

Operational risks:
- Payments can appear successful even if webhook processing is broken
- A bad frontend API base URL can make the live frontend talk to localhost or wrong backend
- Production env drift is possible if local and cloud configs diverge
- SQLite needs explicit recovery planning now that production is real

============================================================
14. IMPORTANT LESSONS LEARNED SO FAR
============================================================

- Webhooks are mandatory for correct Stripe state updates
- Production frontend and production backend must stay aligned
- FRONTEND_URL matters for Stripe redirects
- API base URL in frontend matters a lot
- GitHub deployment greatly reduces manual drift
- Front Door + Storage is valid for HTTPS frontend hosting
- Root domain support is separate from www support and needs explicit DNS / Front Door work
- Strong env management is required before public growth
